# Visualize

Explain it visually and show the result. Default to the previous substantive answer or the explanation in the current conversation. Honor an explicit subject or format. Use existing context without asking the user to repeat it; ask only if no subject can be inferred.

1. Choose the clearest visual form: a diagram for relationships or flows, a chart for measured data, a comparison or timeline for alternatives and sequence, or an annotated image for spatial detail. Default to a lightweight HTML explainer when labels, multiple views, or interaction improve understanding. Use images and video only when they explain something; motion must clarify change over time. Preserve facts, qualifications, and useful source references. Label illustrations, assumptions, and example data; never fabricate screenshots, measurements, or evidence.
2. Read and follow the current Happy `DESIGN.md` at the documentation path supplied in the session's Environment. Use its current variables, fallbacks, components, and acceptance checks rather than copying a stale design spec into the skill. HTML uses a dense neutral surface, system fonts, documented spacing on the 4 px grid, and CSS variables that repaint in light and dark. Embedded content owns its height. Use semantic, keyboard-accessible controls. No fake window chrome, gradients, marketing hero, decorative media, or unsolicited motion. Keep narrative and captions concise.
3. Build the finished artifact with available file, diagram, plotting, or media tools. Read applicable skills when needed. A self-contained HTML document usually needs no framework, server, or live data SDK. Render diagrams rather than pasting source code. Provide meaningful image descriptions. For video, include a usable poster, playback controls, captions or a text equivalent, no autoplay, and a still explanation that remains useful with reduced motion.
4. Verify the content against the explanation, inspect the rendered result, and fix clipped labels, unreadable text, broken assets, or misleading scales. Follow the design document's theme, size, and accessibility checks for HTML. Check media decoding, playback, and captions when applicable. Use available preview tools; if an HTTP preview is necessary, use Happy's dedicated workspace service tools. Report a real verification limit rather than claiming an unseen result works.
5. Discover the current artifact publishing tool and read its schema. Publish the finished result as the appropriate Happy artifact type. HTML uses `index.html`; include every referenced local image, video, poster, caption, stylesheet, or script in the artifact file tree and use relative asset paths. File attachments are copied through the tool's supported file-source fields; host paths and temporary preview URLs are not portable asset links. Include only material authorized for the requested explanation and respect environment reviews.
6. Show the exact tool-returned artifact tag inline in the final reply, with one short sentence explaining what to look at. Use the returned `<happy-artifact id="…"/>` reference, not an invented URL or raw file path, and do not repeat its title. Artifacts and generated media already appear inline; use file-presentation tools for other local deliverables, without displaying the same result twice. Never stop at proposing a visual, pasting HTML or diagram source, or giving an image prompt. If publication is blocked, state the blocker and present the finished file through an available presentation tool when permitted; do not claim it was published.
